# 8.5 fatal-backtrace instrumentation (Phase 0/1)

Lab record for `TODO-8.5-RCE.md`, T0.1–T0.6 and T1.1–T1.5.
Run on 2026-10-23, Docker Desktop / colima on Apple Silicon, `linux/amd64`
under qemu-user emulation. All addresses below are guest addresses from that
emulation (`0x4000...`); native x86_64 uses `0x7f...` but the chunk-relative
offsets are the same measurement.

**Scope warning:** this is a disposable localhost lab. The images and the
preload library are not hardening or production code.

## Results at a glance

| Question | Result |
|---|---|
| Is the stale backtrace-array offset stable? | **Yes, 3/3 fresh workers**: top-level `chunk+0x5a150`, frame `chunk+0x5a118`, args `chunk+0x5a188` |
| Does anything reclaim the 56-byte top-level slot before the consumer dtor? | **No.** The header is byte-identical between producer RSHUTDOWN and the consumer dtor (3/3), and the alloc trace shows no 56-byte allocation at the slot after producer shutdown |
| What actually crashes? | Destroying the still-intact stale array: its nested frame/args/`arData` blocks belong to the reset request heap, so the dtor frees already-free blocks (`zend_mm_heap corrupted`) |
| Can the dtor reach `zif_system` if the zval is controlled? | **Yes, in-process**: a lab `LD_PRELOAD` redirects `EG(last_fatal_error_backtrace)` to a fake 56-byte array with `pDestructor = zif_system`; `id` runs as `www-data` 3/3 |
| Is that proof available remotely? | **No evidence of it.** The consumer warning is emitted before `php_request_startup()`; no attacker-controlled ZendMM allocation runs before the dtor |
| 8.5.12 / `fatal_error_backtraces=0` negatives | No fake-array dtor, no proof, no crash, worker survives (3/3 each) |

## Instrumentation

`gdb` is present but cannot attach: qemu-user returns `ENOSYS` for
`PTRACE_ATTACH` (`ptrace: Function not implemented`). The measurements therefore
use two in-process mechanisms:

1. **`research/85probe/p2s85probe.c`** — a tiny PHP extension. It logs at
   MINIT, RINIT, RSHUTDOWN, module `post_deactivate`, and in a wrapper around
   `zend_error_cb`. At RSHUTDOWN and `post_deactivate` it records the zval
   address/type, `Z_ARRVAL`, GC refcount, chunk base, chunk offset, `arData`,
   `nNumUsed`, `nNumOfElements`, `nTableSize`, `pDestructor`, the frame and
   args hash-table addresses, and the argument zvals (including object handles
   and class names).
2. **`research/85probe/p2s85-preload.c`** — an `LD_PRELOAD` observer. It
   interposes `zval_ptr_dtor`, `zend_error_zstr_at`, `php_request_startup`,
   `php_request_shutdown`, `_emalloc`, `_emalloc_56`, `_efree`, and
   `_efree_56`. The dtor hook acts only when its argument is
   `&EG(last_fatal_error_backtrace)`.

The preload has three modes:

| `P2S85_PRELOAD_MODE` | Behaviour |
|---|---|
| `log` (default) | print the stale zval and header, then call the real dtor (normal crash) |
| `clear` | print, mark the zval `IS_UNDEF`, skip the real dtor, let the request continue |
| `fake` | print, point the zval at an in-process fake `zend_array` with `pDestructor = zif_system`, then call the real dtor |

`P2S85_WATCH=<address>` additionally logs 56-byte allocations/frees that return
or free that exact address. `P2S85_EG_FIELD_OFF` defaults to `0x1b0`
(`&EG(last_fatal_error_backtrace) - &executor_globals` for this build).

Important perturbation: the interposed `zval_ptr_dtor` is visible to the engine,
so hash tables created while the preload is active store the **preload's**
function address in `pDestructor` (`0x40028f8340`) instead of
`libphp+0x7b47a0`. This does not change the zval/header measurements, but it
changes the array-destroy fast path. The no-preload producer log still shows
`pDtor = libphp+0x7b47a0`.

## 8.5 `zend_array` layout used

Confirmed against `Zend/zend_types.h` and the live dumps:

| Field | Offset |
|---|---|
| `gc` (refcount/type) | `0x00` |
| `u.flags` | `0x08` |
| `nTableMask` | `0x0c` |
| `arData` | `0x10` |
| `nNumUsed` | `0x18` |
| `nNumOfElements` | `0x1c` |
| `nTableSize` | `0x20` |
| `nInternalPointer` | `0x24` |
| `nNextFreeElement` | `0x28` |
| `pDestructor` | `0x30` |

This matches `payload.build_ht()` (56-byte `zend_array`, `arData` at `0x10`,
`pDestructor` at `0x30`). The backtrace top-level array is packed
(`flags=0x14`, `nTableSize=8`, `nNumUsed=1`); the frame is a static-key hash
(`flags=0x10`, `nTableMask=0xfffffff0`, `nNumUsed=4`).

## Measurements (8.5.11, producer `/fatal.php?mode=user_error`)

Sequence used by the driver: container start → `GET /index.php` (health, as
`Lab.wait_ready` does) → producer → consumer `GET /consumer/index.php`.

Three fresh workers:

```text
top-level   chunk 0x4008e00000  off 0x5a150   (3/3)
frame[0]    chunk 0x4008e00000  off 0x5a118   (3/3)
args        chunk 0x4008e00000  off 0x5a188   (3/3)
```

The zval lives at `0x4007988ab0` (`&executor_globals + 0x1b0`); the executor
globals are at `0x4007988900`; libphp is loaded at `0x4006200000`.
`zval_ptr_dtor = libphp + 0x7b47a0`; `zif_system = libphp + 0x5996e0`
(the latter is verified by the fake-array proof). The backtrace array is in a
2 MB chunk at `0x4008e00000`, **not** in the `0x4008000000` chunk used by the
validated 8.4 `S` offset. Phase 2 must identify which leaked chunk this is.

A first producer in a freshly started process, before the health request has
warmed the heap, can land one 56-byte slot later (`0x5a150` vs `0x5a118`);
after the health request the layout is stable. The driver always includes the
health request, matching the checker.

The `post_deactivate` log (before `shutdown_memory_manager`) is byte-identical
to RSHUTDOWN, and the consumer dtor sees the same first `0x30` bytes 3/3.

## What reclaims the slot? (T0.5)

Allocation trace with `P2S85_WATCH=0x4008e5a150`; identical in 3/3 runs:

```text
REQ_STARTUP  pid=47                     # producer (/fatal.php)
ALLOC_emalloc56  caller=libphp+0x6e63a1  # transient array during the request
FREE_efree       caller=libphp+0x407b44
ERROR_ENTER type=8192 line=5 zval_type=0
DTOR eg_field type=0
ERROR_ENTER type=256  line=5 zval_type=0
DTOR eg_field type=0
ALLOC_emalloc56  caller=_zend_new_array_0+0x9   # the actual fatal backtrace array
REQ_SHUTDOWN pid=47 bt_type=7
ERROR_ENTER type=2 (E_WARNING) line=0 zval_type=7 value=0x4008e5a150
DTOR eg_field type=7 -> crash
```

There is **no `ALLOC` or `FREE` at the slot between producer shutdown and the
consumer dtor**. The warning's own allocations (the message string, ini
bookkeeping) happen after the dtor, because `zend_error_zstr_at()` starts with:

```c
zval_ptr_dtor(&EG(last_fatal_error_backtrace));
ZVAL_UNDEF(&EG(last_fatal_error_backtrace));
```

Also, the consumer warning runs **before `php_request_startup()`**: the log
shows `ERROR_ENTER` immediately, with no `REQ_STARTUP` for the consumer. This
is the `.htaccess` `php_value` diagnostic path in mod_php (`apply_config()`),
so no request body, query, header, or superglobal has been parsed into
ZendMM at that point.

The earlier transient allocation is a different array in the same 56-byte bin;
the slot is freed and later reused for the actual backtrace array during the
producer's fatal error. It is not reused again after shutdown.

### Why it crashes

The stale top-level array is intact, including `arData` and the frame/args
headers (dumped at the consumer dtor). The crash is a **double free**: the
request heap was reset by fast shutdown, and `zend_array_destroy()` walks the
stale array and `efree()`s blocks that ZendMM already owns again. The
`zend_mm_heap corrupted` abort is allocator metadata detection, not a call
through a controlled pointer.

Implication for the planned Phase 3: there is no window in this consumer in
which an attacker-controlled 56-byte allocation can overwrite the stale header.
The "reclaim the slot" premise is not supported by the mod_php `.htaccess`
warning path. Reaching a controlled `pDestructor` remotely needs a different
early consumer that performs an attacker-influenced ZendMM allocation before
`zend_error_zstr_at()`, or a producer-side primitive that leaves controlled
bytes at `chunk+0x5a150` across request shutdown. `ZVAL_UNDEF` in 8.5.12
removes the stale zval before any of this can happen.

## Phase 1 — instrumented control proof

`P2S85_PRELOAD_MODE=fake` redirects the stale zval at the dtor to a static
56-byte fake array (layout above), with `arData` pointing at a fake
`execute_data`/bucket and `pDestructor = libphp + 0x5996e0`. The fake string is
`id > /out/rce85-instrumented-proof`.

Measured, 8.5.11, 3/3 fresh workers:

```text
consumer ERROR_ENTER type=2 zval_type=7 value=0x4008e5a150
redirected stale zval to fake array 0x40028fb080, pDestructor=0x40067996e0
proof: uid=33(www-data) gid=33(www-data) groups=33(www-data)
worker replaced, "zend_mm_heap corrupted"/exit signal recorded
```

This proves the consumer's dtor can call `zif_system` **if the zval/array is
controlled in-process**. It is not a remote primitive: the redirect is done by
`LD_PRELOAD` at the dtor, a capability the attacker does not have.

Negatives (3/3 each):

| Case | Consumer zval | Proof | Crash / worker replaced |
|---|---|---|---|
| `php2shell:8.5.12-debug`, `fatal_error_backtraces=1` | `UNDEF` (type 0) | none | no / no |
| `php2shell:8.5.11-debug`, `fatal_error_backtraces=0` | `UNDEF` (type 0) | none | no / no |

On 8.5.12 the producer still creates the backtrace (RSHUTDOWN sees it), but the
fix clears `EG(last_fatal_error_backtrace)` during shutdown; the consumer sees
`UNDEF`. On 8.5.11 with `fatal_error_backtraces=0`, no backtrace is created.

## Reproduction

```bash
# Preload library (mounted by the driver at /preload)
docker run --rm --platform linux/amd64 \
  -v "$PWD/research/85probe:/src:ro" -v "$PWD/out/test85/preload:/preload" \
  php2shell:8.5.11-debug \
  sh -c 'gcc -shared -fPIC -O2 -Wall -o /preload/p2s85-preload.so /src/p2s85-preload.c -ldl'

# Phase 0: stability + intact-header check (3 fresh workers)
uv run python research/phase0_85.py --image php2shell:8.5.11-debug \
  --mode log --runs 3 --label vuln85-log

# Phase 0: allocation trace at the stale slot
uv run python research/phase0_85.py --image php2shell:8.5.11-debug \
  --mode log --runs 3 --watch 0x4008e5a150 --label vuln85-watch

# Phase 1: instrumented proof and negatives
uv run python research/phase0_85.py --image php2shell:8.5.11-debug \
  --mode fake --runs 3 --label vuln85-fake
uv run python research/phase0_85.py --image php2shell:8.5.12-debug \
  --mode fake --runs 3 --label fixed85-fake
uv run python research/phase0_85.py --image php2shell:8.5.11-debug \
  --mode fake --fatal 0 --runs 3 --label vuln85-fake-nofatal
```

JSON per suite); proof files are `out/.../out/rce85-instrumented-proof`.

## Caveats

- QEMU user-mode emulation fixes the address layout (`0x4000...`) and makes it
  reproducible here; native x86_64 will differ. Chunk-relative offsets are the
  portable part, and even those are image/allocator-specific.
- `LD_PRELOAD` interposition changes `pDestructor` and adds observer overhead;
  it is suitable for measurement, not for claiming stock-image behaviour.
- The debug image adds an extension to MINIT, which can shift early allocations.
  The 8.5 crash oracle remains the stock-image check.
- No remote leak or remote reclaim was attempted in Phase 0/1. The next step is
  Phase 2 (8.5 leak re-calibration), but the T0.5 result should be resolved
  first: the current mod_php consumer has no pre-dtor attack-controlled
  allocation window.

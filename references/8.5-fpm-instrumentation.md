# 8.5 fatal-backtrace on FPM (Phase 3 pivot)

> Consolidated research log: [`8.5-rce-research-log.md`](8.5-rce-research-log.md)
> (Phase 0/1, FPM pivot, heap grooming, and the structural blocker).


Lab record for the FPM pivot requested after Phase 0/1. Read
[`8.5-rce-instrumentation.md`](8.5-rce-instrumentation.md) first; this file
only records what changes on the FPM SAPI.

**Scope:** disposable localhost lab, pinned images, benign `id` proof. The
FPM images are debug/instrumentation builds; the stock image is never modified.

## Why FPM looked better

In `sapi/fpm/fpm/fpm_main.c`, `init_request_info()` runs **before**
`php_request_startup()`:

```c
init_request_info();          /* auth, PHP_VALUE, PHP_ADMIN_VALUE */
...
if (UNEXPECTED(php_request_startup() == FAILURE)) { ... }
```

`init_request_info()`:

1. copies the script path with `estrdup()` (`path_translated`),
2. calls `php_handle_auth_data(HTTP_AUTHORIZATION)` — `php_base64_decode()`
   plus a binary-safe `estrndup()` (`auth_user`),
3. parses `PHP_VALUE` / `PHP_ADMIN_VALUE` with `spprintf()` +
   `zend_parse_ini_string()`.

An invalid `PHP_VALUE` such as `memory_limit=999999999999999999999` reaches
`zend_error_zstr_at()` **before** `init_executor()` clears
`EG(last_fatal_error_backtrace)`, exactly like the `.htaccess` path. The
difference is that FPM can perform attacker-influenced ZendMM allocations
before that dtor.

## Wiring

- one worker: `pm = static`, `pm.max_children = 1`
- `listen = 0.0.0.0:9000`, published only on `127.0.0.1`;
  `listen = 127.0.0.1:9000` did not accept the host-mapped connection from the
  Docker port forwarder in this environment
- `clear_env = no`, `catch_workers_output = yes`
- per-run `/usr/local/etc/php-fpm.conf` and
  `conf.d/zz-backtrace.ini` (`fatal_error_backtraces=1`,
  `zend.exception_ignore_args=0`)
- `research/fcgi_client.py` sends explicit FastCGI params
  (`SCRIPT_FILENAME`, `PHP_VALUE`, `HTTP_AUTHORIZATION`, ...)
- `research/phase0_85_fpm.py` drives the producer/consumer and parses the
  extension log

`LD_PRELOAD` does **not** work for this pivot: `php-fpm` is a PIE executable
whose internal calls are bound directly, so the Apache preload hooks never run.
The instrumentation is therefore in the extension:
`P2S85_EXT_MODE=log|clear|fake`, and the fake redirect happens in the producer's
`post_deactivate` (before `shutdown_memory_manager()`), using a static buffer
that survives the heap reset.

## Measurements (8.5.11 FPM, QEMU amd64)

Producer: FastCGI `GET /fatal.php?mode=user_error`.
Consumer: FastCGI `GET /consumer/index.php` with
`PHP_VALUE=memory_limit=999999999999999999999`.

| Object | Value |
|---|---|
| chunk | `0x4006400000` |
| top-level backtrace array | `chunk + 0x5c150` |
| frame hash | `chunk + 0x5c118` |
| args hash | `chunk + 0x5c188` |
| `zif_system` (from `CG(function_table)["system"]->handler`) | `0x400060e3a0` |
| `zval_ptr_dtor` (FPM executable) | `0x4000829460` |
| `auth_user` (56-byte `estrndup`) | `0x4006404000` |

The offsets are stable 3/3 fresh workers. The FPM numbers are **not** the
libphp numbers (`zif_system` `0x5996e0`, `zval_ptr_dtor` `0x7b47a0`); any
Phase 2 leak work needs a separate FPM profile.

### Pre-startup crash

`P2S85_EXT_MODE=log`, 3/3:

```text
producer: fatal error, RSHUTDOWN sees ARRAY at chunk+0x5c150
consumer: init_request_info -> invalid PHP_VALUE -> zend_error_zstr_at
          -> zval_ptr_dtor(stale array) -> double free
          -> zend_mm_heap corrupted / child exited on signal 6
```

No `RINIT` for the consumer (the warning precedes `php_request_startup()`),
which is the FPM equivalent of the mod_php ordering. FPM respawns the worker
after the abort, so a health check is not a crash oracle by itself; the worker
PID change and the `exited on signal` log line are.

### Instrumented proof

`P2S85_EXT_MODE=fake`, 3/3:

```text
consumer warning dtors the fake zval installed at producer post_deactivate
proof: uid=33(www-data) gid=33(www-data) groups=33(www-data)
worker replaced / SIGABRT after the proof
```

Negatives, 3/3 each:

| Case | Consumer zval | Proof | Crash |
|---|---|---|---|
| `php2shell:8.5.12-fpm-debug`, `fatal_error_backtraces=1` | `UNDEF` | none | no |
| `php2shell:8.5.11-fpm-debug`, `fatal_error_backtraces=0` | `UNDEF` | none | no |

This proves the FPM pre-startup dtor can reach `zif_system` **if the zval is
controlled in-process**. It is still an instrumentation proof, not a remote
primitive.

## The attacker-controlled pre-startup allocation

`HTTP_AUTHORIZATION: Basic <base64>` is binary-safe up to the first `:`
because `php_handle_auth_data()` does:

```c
user = php_base64_decode(auth + 6, ...);
pass = strchr(ZSTR_VAL(user), ':');   /* C string semantics! */
*pass++ = '\0';
SG(request_info).auth_user = estrndup(ZSTR_VAL(user), ZSTR_LEN(user));
```

A 55-byte decoded payload becomes a 56-byte `_emalloc_56` block. The fake
header can use the colon at offset 0 (the only position before the first NUL;
the `strchr` stops at the first NUL), with:

| Offset | Value |
|---|---|
| `0x00` | `:` (zeroed by `*pass = 0`) |
| `0x04` | `IS_ARRAY` (type 7) |
| `0x08` | `0x10` / `0xFFFFFFF8` |
| `0x10` | `arData` |
| `0x18` | `nNumUsed = 1`, `nNumOfElements = 1` |
| `0x30` | `pDestructor = zif_system` (byte 7 is the `estrndup` NUL) |

Measured with `P2S85_EXT_MODE=clear` (so the consumer survives and logs RINIT),
3/3:

```text
auth_user = 0x4006404000
slot      = 0x400645c150
slot header at consumer RINIT: unchanged (original backtrace array)
auth_user != slot
```

With `P2S85_EXT_MODE=log` and the same auth payload, the consumer still crashes
on the original stale array and **no proof** is written (3/3). The auth payload
is a genuine remote-controlled pre-startup 56-byte allocation, but it does not
land on the stale slot.

### Why

`shutdown_memory_manager(..., full=0)` resets the main chunk and rewinds the
allocator's free tail to the start of the chunk. The next request's first
56-byte pages come from the beginning (`auth_user` at `0x4006404000`), while
the stale slot is at `0x400645c150`, about 90 pages later. `init_request_info()`
only has a handful of pre-auth ZendMM allocations (path copy, base64 string,
`auth_user`); it cannot consume ~90 pages of the 56-byte bin before the
warning. `PHP_VALUE` comes **after** auth and its per-entry strings are text,
not a fake array.

So the simple FPM header does not reclaim the slot either. A remote chain still
needs one of:

1. a producer-side groom that places the backtrace array in the first
   56-byte page after the reset (the slot is `chunk+0x5c150` today);
2. a repeatable pre-auth binary allocation that can spray the 56-byte bin
   (auth is once per request; path copies are text);
3. a different early consumer where attacker data is parsed into ZendMM
   before `zend_error_zstr_at()`.

## Heap grooming attempts (2026-10-23)

The first FPM measurement left the producer array at `chunk+0x5c150` and the
consumer auth at `chunk+0x4000`. Several grooms were tried:

| Groom | Result |
|---|---|
| Producer `HTTP_AUTHORIZATION` with a 55-byte decoded Basic payload (no password), then `fatal_min.php` | **Backtrace moved to the low 56-byte page**: top-level `chunk+0x4150`, frame `chunk+0x41c0`, args `chunk+0x41f8`; producer `auth_user` `chunk+0x4000` |
| Same, with a 54-byte password | top-level `chunk+0x4188` (one slot later) |
| Opcache warm-up (`/fatal.php?mode=require` or `exception`) before the producer | top-level `chunk+0x5c118` (one slot earlier, still far) |
| Minimal producer (`docker/www/fatal_min.php`) | top-level `chunk+0x5b118` (about one page lower) |
| Producer `PHP_VALUE=memory_limit=300000..800000` | no change (`0x5c118`); the first ZendMM chunk is 2 MB, so these limits do not OOM during startup |
| Large Basic-auth UAF (fake array inside a 360 KB decoded `user` string) | rejected by FastCGI: `FCGI_MAX_LENGTH` is 65,535 per record and `fcgi_read_params` rejects a name/value pair split across records |
| Consumer `auth_user` reclaim of the low producer slot | not aligned |

The last row is the blocker. The producer's top-level array is at slot
`0x150` of the 56-byte page (`chunk+0x4000+0x150` = `0x4150`), while the
consumer's first 56-byte allocation (`auth_user`) is slot `0` (`0x4000`).
The producer has five live 56-byte request-startup allocations (hash tables such
as the symbol table and included files) between its pre-startup `auth_user`
slot and the backtrace array; the consumer's warning is **before**
`php_request_startup()`, so those allocations do not exist yet. `init_request_info()` only offers a few pre-auth 56-byte
allocations (path copy, `PATH_INFO`/`PATH_TRANSLATED` buffers, auth user), so
the auth payload lands at slot 0-3, not slot 6-7.

The FastCGI 65 KB per-value cap also rules out the large-payload UAF: a
decoded payload large enough to cover `chunk+0x5c150` (about 360 KB) needs a
base64 value of about 480 KB, which cannot fit in a FastCGI param record. The
same cap limits any binary-controlled pre-startup spray.

**Conclusion:** the groom moves the producer array to the right page but not
to the right slot, and the pre-startup consumer cannot fill the five-slot gap.
No remote 8.5 RCE was achieved. The instrumented fake-array proof remains the
positive control; the stock crash/UAF oracle remains the supported check.

## Caveats

- FPM debug images add the extension and use a custom pool/php-fpm.conf; the
  validated 8.4 chain still uses its own images and `docker/php-lab.ini`.
- Addresses are qemu-user guest addresses; chunk-relative offsets are the
  portable measurement, and they are still image/allocator-specific.
- The fake proof is an in-process `post_deactivate` redirect. It is useful as a
  control, not as a remote exploit.
- The FPM `Auth` experiment uses the decoded payload's first byte as the colon;
  that zeroes the array's `gc.refcount`. The dtor path is expected to tolerate
  it in this release build (`GC_REMOVE_FROM_BUFFER` sees no GC info bits), but
  this was **not** exercised at the slot because the allocation never landed
  there. Validate it if a groom ever places the payload at
  `chunk+0x5c150`. This is lab-only.

# 8.5 fatal-backtrace RCE research log

Consolidated record of the 8.5 investigation: Phase 0 instrumentation, Phase 1
instrumented proof, the FPM pivot, and the heap-grooming attempts.

Date: 2026-10-23. Environment: Docker Desktop / colima on Apple Silicon,
`linux/amd64` under qemu-user emulation.

**Result: no remote 8.5 RCE.** The consumer warning can be made to call
`zif_system` if the stale zval is controlled **in-process**, but no tested
remote/allocation primitive places a controlled array at the stale slot.
The shipped 8.5 check remains the crash/UAF oracle.

The focused records are:

- [`8.5-rce-instrumentation.md`](8.5-rce-instrumentation.md) — mod_php Phase 0/1
- [`8.5-fpm-instrumentation.md`](8.5-fpm-instrumentation.md) — FPM pivot
- [`../TODO-8.5-RCE.md`](../TODO-8.5-RCE.md) — backlog and decisions

## Safety and scope

- Localhost Docker only; pinned images; one worker; benign `id` proof.
- No persistence, reverse shell, or destructive payload.
- The debug images and extension/preload are lab-only and must not be deployed.
- `docker/php-lab.ini` is untouched; the validated 8.4 chain still uses it.

## 1. The bug in one page

### 8.5.11

`zend_shutdown_executor_values()` has a fast path when ZendMM is active:

```c
if (!fast_shutdown) {
    ...
    zval_ptr_dtor(&EG(last_fatal_error_backtrace));
    ZVAL_UNDEF(&EG(last_fatal_error_backtrace));
    ...
}
zend_objects_store_free_object_storage(&EG(objects_store), fast_shutdown);
```

On 8.5.11 the fast path skips both the dtor and the reset. The request heap is
subsequently reset by `shutdown_memory_manager(..., full=0)`, but
`EG(last_fatal_error_backtrace)` still holds a pointer into the freed request
heap.

The next request can reach that pointer **before `init_executor()`** via
`zend_error_zstr_at()`:

```c
zval_ptr_dtor(&EG(last_fatal_error_backtrace));
ZVAL_UNDEF(&EG(last_fatal_error_backtrace));
```

`zend_error_zstr_at()` starts with this dtor. In mod_php, the `.htaccess`
`php_value` diagnostic is applied by `apply_config()` before request startup.
In FPM, `init_request_info()` applies `PHP_VALUE`/`PHP_ADMIN_VALUE` and parses
`HTTP_AUTHORIZATION` before `php_request_startup()`. Both can therefore dtor
the stale backtrace.

### 8.5.12

The fix (commit `3584a98bda`, see
[`fix-commit-3584a98bda.md`](fix-commit-3584a98bda.md)) adds, after
`zend_objects_store_free_object_storage()`:

```c
/* may be used by zend_error_zstr_at before init_executor */
ZVAL_UNDEF(&EG(last_fatal_error_backtrace));
```

It clears the pointer without freeing it; the request heap is already gone. The
next request sees `IS_UNDEF` and the pre-init dtor is harmless.

### What crashes

The stale array is still structurally intact at the dtor. The crash is not a
controlled call: `zend_array_destroy()` walks the stale top-level array and its
nested frame/args/`arData` blocks, which belong to the reset heap, and frees
already-free blocks. ZendMM reports `zend_mm_heap corrupted` / `SIGABRT`.

The research question is whether an attacker can replace the stale array with
a fake `zend_array` whose `pDestructor` is `zif_system`, before that dtor.

### Instrumentation

`gdb` is installed but cannot attach: qemu-user returns `ENOSYS` for
`PTRACE_ATTACH`. Two in-process mechanisms replace it:

1. **`research/85probe/p2s85probe.c`** — a PHP extension.
   - MINIT: opens `/out/p2s85-probe.log`, resolves
     `system` from `CG(function_table)` to `zif_system`, sets `P2S85_ZIF`, and
     wraps `zend_error_cb`.
   - RINIT/RSHUTDOWN: logs the stale zval, array header, chunk base/offset,
     `arData`, counts, `pDestructor`, frame/args, and arg zvals.
   - `post_deactivate`: logs the array **before** `shutdown_memory_manager()`;
     supports `P2S85_EXT_MODE=clear|fake`.
   - `fake`: installs a static 56-byte fake array with
     `pDestructor = zif_system` and clears the original pointer. This survives
     the heap reset and is dtored by the consumer warning.
2. **`research/85probe/p2s85-preload.c`** — an `LD_PRELOAD` observer used for
   mod_php. It interposes `zend_error_zstr_at`, `zval_ptr_dtor`,
   `php_request_startup/shutdown`, `_emalloc`, `_emalloc_56`, `_efree`, and
   `_efree_56`. It logs the exact pre-dtor state and supports `log|clear|fake`.

`LD_PRELOAD` does **not** work for FPM: `php-fpm` is a PIE executable whose
internal calls are bound directly, so the preload hooks never run. FPM uses the
extension instead.

Perturbation note: the preload's `zval_ptr_dtor` interposition changes the
`pDestructor` stored in hash tables created while it is active (the pointer
resolves to the preload). Header/zval measurements are unaffected; the
instrumented proof accounts for this.

## 3. Phase 0 — mod_php measurements

Sequence: container start → `GET /index.php` (health) → producer
`/fatal.php?mode=user_error` → consumer `/consumer/index.php` (invalid
`php_value memory_limit`).

Three fresh workers, 8.5.11:

| Object | Chunk-relative offset |
|---|---|
| top-level backtrace array | `chunk + 0x5a150` |
| frame hash | `chunk + 0x5a118` |
| args hash | `chunk + 0x5a188` |

The chunk was `0x4008e00000` under qemu; libphp was at `0x4006200000`.
`zval_ptr_dtor = libphp + 0x7b47a0`; `zif_system = libphp + 0x5996e0`.

### Layout

Confirmed against `Zend/zend_types.h` and live dumps:

| Field | Offset |
|---|---|
| `gc.refcount/type` | `0x00` |
| `u.flags` | `0x08` |
| `nTableMask` | `0x0c` |
| `arData` | `0x10` |
| `nNumUsed` | `0x18` |
| `nNumOfElements` | `0x1c` |
| `nTableSize` | `0x20` |
| `nInternalPointer` | `0x24` |
| `nNextFreeElement` | `0x28` |
| `pDestructor` | `0x30` |

All three backtrace headers are 56-byte `_emalloc_56` blocks. The top-level is
packed (`flags=0x14`, `nTableSize=8`); the frame is a static-key hash
(`flags=0x10`, `nTableMask=0xfffffff0`, 4 elements).

### Reclaim trace (T0.5)

`P2S85_WATCH=0x4008e5a150` produced this sequence identically 3/3:

```text
REQ_STARTUP producer
ALLOC_emalloc56 (transient array during the producer)
FREE_efree
ERROR_ENTER type=8192 zval_type=0
DTOR type=0
ERROR_ENTER type=256 zval_type=0
DTOR type=0
ALLOC_emalloc56 caller=_zend_new_array_0+0x9   # actual backtrace array
REQ_SHUTDOWN bt_type=7
ERROR_ENTER consumer type=2 zval_type=7 value=0x4008e5a150
DTOR type=7 -> crash
```

There is **no allocation/free at the slot** between producer shutdown and the
consumer dtor. The header is byte-identical at RSHUTDOWN and at the dtor
3/3. The consumer warning has no `REQ_STARTUP`: it is pre-startup, so no
request body/query/header is parsed into ZendMM.

The crash is the stale array's nested double free, not a fake `pDestructor`.

## 4. Phase 1 — instrumented proof

|---|---|
| `0x00` | refcount 1, type `IS_ARRAY` |

## 5. FPM pivot

### Ordering

In `sapi/fpm/fpm/fpm_main.c`:

```c
init_request_info();          /* auth, PHP_VALUE, PHP_ADMIN_VALUE */
...
if (UNEXPECTED(php_request_startup() == FAILURE)) { ... }
```

`init_request_info()` copies the script path, calls
`php_handle_auth_data(HTTP_AUTHORIZATION)`, then parses `PHP_VALUE` /
`PHP_ADMIN_VALUE`. An invalid `memory_limit` reaches
`zend_error_zstr_at()` before `init_executor()`.

One worker (`pm=static`, `pm.max_children=1`), explicit FastCGI params. The pool
listens on `0.0.0.0:9000`, published only on `127.0.0.1`; `listen=127.0.0.1`
did not accept the host-mapped connection through the Docker port forwarder in
this environment.

### Measurements (8.5.11 FPM, no groom)

| Object | Value |
|---|---|
| chunk | `0x4006400000` |
| top-level | `chunk + 0x5c150` |
| frame / args | `chunk + 0x5c118` / `chunk + 0x5c188` |
| `zif_system` | `0x400060e3a0` |
| `zval_ptr_dtor` | `0x4000829460` |

The pre-startup warning crashes the worker 3/3. The extension fake proof is
3/3; 8.5.12 and `fatal_error_backtraces=0` are 0/3.

### The Authorization allocation

`php_handle_auth_data()`:

```c
user = php_base64_decode(auth + 6, auth_len - 6);
pass = strchr(ZSTR_VAL(user), ':');   /* C string semantics */
*pass++ = '\0';
SG(request_info).auth_user = estrndup(ZSTR_VAL(user), ZSTR_LEN(user));
```

- The decoded payload is binary-safe for `estrndup`, but `strchr` stops at the
  first NUL. The colon must be at offset 0 to be found before the first NUL.
- `*pass = 0` therefore zeroes the first payload byte.
- A 55-byte decoded payload gives a 56-byte `auth_user` allocation.
- The fake array header can live at offset 0/absolute, with
  `pDestructor = zif_system`, and the execute-data/command later in the same
  block. The colon-zeroed `gc.refcount` is tolerated by
  `GC_REMOVE_FROM_BUFFER` in this release build (it checks the GC info bits),
  but this was not exercised at the slot.

Measured with `clear` mode, 3/3:

```text
auth_user = 0x4006404000
slot      = 0x400645c150
slot header at consumer RINIT: unchanged (original backtrace array)
```

With `log` mode the consumer still crashes on the original array and writes no
proof (0/3). The auth allocation is real and attacker-controlled, but it does
not land on the slot.

## 6. Heap grooming

### ZendMM mechanics

At request shutdown, `zend_mm_shutdown(heap, full=0, …)`:

- moves non-main chunks to the cache,
- reinitializes the main chunk: `free_tail = ZEND_MM_FIRST_PAGE`,
  `free_pages` reset, `free_slot` bins cleared.

The next request allocates pages with a **best-fit** search over the free map.
The first 56-byte page after reset is near the start of the chunk. The stale
producer slot is at the end of the producer's full request heap. That is the
initial gap.

### Producer auth groom

A **pre-startup** Basic auth in the producer allocates a 56-byte `auth_user`
before the request startup. That forces the first 56-byte page to
`chunk+0x4000`. The later backtrace array can then land on that page:

| Producer request | Top-level | Frame | Args | Producer auth_user |
|---|---|---|---|---|
| `/fatal_min.php`, no auth | `chunk+0x5b118` | `0x5b188` | `0x5b1c0` | — |
| `/fatal_min.php`, 55-byte auth, no password | **`chunk+0x4150`** | `0x41c0` | `0x41f8` | `0x4000` |
| same, with a 54-byte password | `chunk+0x4188` | `0x41f8` | `0x4230` | `0x4000` (password `0x4038`) |

56-byte slots are `0x38` apart:

```text
0x4000  slot 0   producer auth_user
0x4038  slot 1   producer auth_password (when present)
...
0x4150  slot 6   producer backtrace top-level (no-password case)
0x4188  slot 7   producer backtrace top-level (password case)
```

This is a real groom: the stale array moved from the far page (`0x5c150`) to
the low 56-byte page (`0x4150`).

### Consumer budget

The consumer warning is pre-startup. The 56-byte allocations available before
`auth_user` are limited:

| Allocation | Slot effect |
|---|---|
| `path_translated` (SCRIPT_FILENAME length 48–55) | one live slot |
| `PATH_INFO` / `PATH_TRANSLATED` buffers (length 48–55) | one or two, often freed before auth |
| `auth_user` (55-byte decoded) | the target slot |
| `auth_password` (after auth_user) | after the target, does not shift it |
| `user` zend_string | 80-byte bin for a 55-byte payload |
| `PHP_VALUE` parser | after auth; values are text, not a fake array |

So `auth_user` lands at slot 0–3, while the producer top-level is at slot 6–7.
The producer has five live 56-byte request-startup allocations between its
pre-startup auth slot and the backtrace. At least two are identifiable in
`Zend/zend_execute_API.c`:

```c
zend_hash_init(&EG(symbol_table), 64, NULL, ZVAL_PTR_DTOR, 0);   /* line 154 */
zend_hash_init(&EG(included_files), 8, NULL, NULL, 0);           /* line 158 */
```

The remaining slots are related startup allocations (the exact five were not
symbolically attributed). None of them exist in the consumer before
`php_request_startup()`. The gap is structural.

### Other attempts

| Attempt | Result |
|---|---|
| Opcache warm-up before the producer | top-level `0x5c118` (one slot earlier) |
| Minimal producer (`fatal_min.php`) | top-level `0x5b118` (about one page lower) |
| Producer `PHP_VALUE=memory_limit=300000..800000` | no change; the first ZendMM chunk is 2 MB, so the limit does not OOM during startup |
| Large Basic-auth UAF (fake array inside a ~360 KB decoded `user` string) | rejected by FastCGI: `FCGI_MAX_LENGTH` is 65,535 per record; `fcgi_read_params()` rejects a name/value pair split across records |
| Consumer path padding / PATH_INFO | can shift `auth_user` by 1–2 slots, not 6 |
| Large-auth bytes at the slot | impossible under the 65 KB param cap |

The large-UAF idea was otherwise sound: `php_base64_decode` allocates the
decoded `user` string, `auth_user` copies it, and the `user` block is freed
before the `PHP_VALUE` warning. With a large enough block, the stale slot could
contain attacker bytes. The FastCGI per-record cap prevents the required size.

## 7. Why the remote chain is blocked

The pre-init consumer has an empty request heap; the producer's backtrace is at
the end of a full request heap. The gap is five 56-byte startup allocations
plus the backtrace layout. The only pre-startup attacker-controlled allocation
with useful bytes is `auth_user`, and the FastCGI cap limits the encoded value
to 65,535 bytes (about 49 KB decoded).

To get remote code execution one of these would be required:

1. a **pre-startup 56-byte spray** of at least six controlled blocks, which
   `init_request_info()` does not provide;
2. a **producer** that creates the backtrace at slot 0–3, which requires a
   fatal before the request startup tables exist; the tested early-fatal
   producers (parse error, missing require) do not create a backtrace;
3. a **different early consumer** that parses attacker data into ZendMM before
   `zend_error_zstr_at()` and before `init_executor()`;
4. a different corruption primitive that does not depend on the 56-byte slot
   (for example, controlling the nested `arData`), which would need its own
   allocator analysis and was not demonstrated.

## 9. Limitations and caveats

- Addresses are qemu-user guest addresses (`0x400...`); native x86_64 uses
  `0x7f...`. Chunk-relative offsets are the portable measurement, but they are
  still image/allocator-specific.
- The debug images add an extension and, for mod_php, a preload. The stock image
  is never modified. The 8.5 crash oracle remains the stock-image check.
- `LD_PRELOAD` changes `pDestructor` resolution on mod_php; the pre-dtor header
  measurements and the extension-based FPM proof do not depend on it.
- The five-slot startup attribution is inferred from the slot gap; the
  extension does not symbolically resolve each startup allocation.
- The auth fake header's colon-at-offset-0 zeroes `gc.refcount`; the dtor path
  is expected to tolerate it, but the payload was never placed at the slot, so
  that specific header was not end-to-end exercised.
- FastCGI param behavior is `libfcgi` in `main/fastcgi.c`; nginx/Apache limits
  may be smaller than 65 KB in a real deployment.
- The consumer requires a server-side invalid `PHP_VALUE`/`.htaccess`
  diagnostic. The attacker does not normally control that directive; the lab
  supplies it, matching the existing checker's consumer.
- No FPM RCE stage is shipped. The checker's 8.5 path remains the crash/UAF
  oracle; the 8.4 RCE chain is unaffected.

## 10. Recommendation

Freeze 8.5 at the crash/UAF oracle unless a genuinely different early consumer
or primitive is found. The current `.htaccess`/`PHP_VALUE` warning consumer is
pre-startup and structurally cannot reach the producer backtrace slot at a
controlled index. The instrumented proof is valuable evidence that the dtor is
exploitable in principle, but it should not be described as a remote exploit.

If the research continues, the most promising direction is a new **pre-init
consumer** that parses attacker-controlled data into ZendMM (then a slot/spray
could be engineered), not more grooming of the existing warning path.
